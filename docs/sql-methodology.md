# SQL 复现与指标口径

这组 MySQL 8.0 脚本基于原项目十个分析模块整理，保留用户与商品分析范围。原始表不做删除或更新，分析在 `user_behavior_clean` 和派生汇总表上执行。所有日期均采用北京时间，SQL 设置会话时区为 `+08:00`，对应本项目观察期的 `Asia/Shanghai`。

## 执行方式

1. 在独立分析环境执行 `sql/00_schema.sql`，创建数据库 `taobao_user_operations` 及空表 `user_behavior`。
2. 将无表头的 `UserBehavior.csv` 按原始文件行顺序导入五个字段：`user_id,item_id,category_id,behavior_type,timestamps`。自动生成的 `id` 用于保留同一去重键下最早的源行。不要把同一文件重复导入原始表。脚本中的 `LOAD DATA LOCAL INFILE` 是注释示例，文件路径由运行者按实际位置填写；如服务端禁用 LOCAL，可使用数据库客户端的 CSV 导入功能。
3. 依次执行 `01` 至 `10`。`01` 建立清洗表和公用用户日、用户汇总；后续模块依赖这些表。脚本会清空并重建自身的派生结果表，因此应在没有其他写入任务的分析数据库中运行。
4. 执行 `11_validation.sql` 查看固定样本控制总量和指标不变量。固定总量检查应全部返回 `PASS`；不变量的 `violations` 应全部为零。

如已有项目数据库，先确认原表具有稳定的源行编号 `id`。原文件没有编号时，按文件顺序重新导入 `00` 创建的空表更容易保证去重结果可复现。直接给任意排序的旧表追加自增字段，并不能证明编号等同于 CSV 源行顺序。

原始约 1 亿行数据不会随仓库分发。全量 MySQL 运行需要原表、清洗副本、二级索引、派生表及窗口函数临时空间，建议预留数十 GB 空间，并按实际机器资源评估。`01` 的全局去重、`06` 的用户商品组合、`09`/`10` 的商品聚合可能耗时较长。脚本没有修改任何 GLOBAL 缓存或认证配置。示例数据适合检查流程；得到文档中的全量数字需要完整数据源。

## 指标定义

- **清洗**：观察窗口为 `[2017-11-25 00:00:00, 2017-12-04 00:00:00)`。去重键为 `(user_id,item_id,timestamps)`，保留最小源行 `id`。同一键的记录时间相同，因此先截取时间窗口再去重，不会改变窗口内保留的源行。缺失必要字段、未知行为类型不会进入分析表；本次全量原数据字段空值为零。
- **PV、UV、浏览深度**：PV 为 `pv` 行数；UV 为当日发生过 `pv` 的去重用户数；浏览深度为日 PV/日 UV。它们描述浏览活跃，不表示新增用户获客。
- **留存**：某日发生任意行为的去重用户中，次日仍发生任意行为的用户占比。不是首次获客人群留存。12 月 3 日之后没有观测数据，因此末日留存为 `NULL`，不能当作 0。
- **单次行为用户占比**：全窗口仅一条行为的用户数/全窗口去重用户数。数据缺少会话标识，这不是会话跳出率。
- **用户购买占比**：有浏览且有购买的用户数/有浏览的用户数，保证分子属于分母人群。购买次数/PV 是另一项事件次数比，不能混用人数和次数。
- **三层漏斗**：浏览用户；同时有收藏或加购的浏览用户；同时有购买的前一层用户。各层是观察期内用户行为交集，不限定同一商品，也不验证时间先后。`funnel_users` 为每层人数；两个转化字段均存 0—1 比例，展示时再转换为百分数。
- **购买行为组合**：发生过购买的用户—商品对，在九天内是否还出现浏览、收藏、加购。四位编码顺序为 PV、收藏、加购、购买。组合采用“＋”命名；“仅购买”仅表示窗口内缺少该用户对该商品的其他三种记录，不等于业务中未浏览过。组合数量不是人数、订单数或购买次数。
- **RF**：只对购买用户计算。R 使用原项目的最近购买日五档分数；F 对购买行为次数使用 `NTILE(5) OVER (ORDER BY buy,user_id)`。没有金额字段，因此不计算 Monetary。表名 `rfm_model` 为兼容历史看板保留。
- **商品/品类购买用户占比**：该商品/品类的去重购买用户数/发生任意行为的去重用户数，保留分母 `users` 和分子 `buyers`。不是严格的浏览人群或时序转化率。补充示例排行使用商品至少 100 人、品类至少 1,000 人的门槛；门槛是分析筛选，不是统计显著性保证。
- **热门榜单**：按 PV 排序。各品类热门商品按行为记录的 `(category_id,item_id)` 分组，保留品类内并列第一，再从这些候选中选 PV 最大的前 20 行。不能把多品类商品任意归到一个品类后再排名。

## RF 评分的可复现性

原 SQL 的 `NTILE` 只按频次排序，同频次用户的分组顺序没有规定。公开版补充 `user_id` 作为排序依据，分层与全量复核结果采用同一规则。等人数分箱仍可能给相同购买次数不同分数，因此这些分层是评分规则下的用户划分。

当前 672,404 个购买用户对应的 F 评分均值为约 `2.9999970256`。评分均值使用 `SUM(score)*1e0/COUNT(*)` 保留比较精度，避免某些 MySQL 定点平均值舍入为 `3.0000` 后改变严格大于/小于的分组。原项目的严格比较逻辑保留；若新数据恰好等于某评分均值，则显式标为“边界待分类”，不会静默丢失。当前全量控制样本没有边界用户。更换评分规则、样本或同分排序后，应重新计算并更新看板，不能沿用旧占比。

## 已整理的问题与验证边界

公开 SQL 修复了原稿中的时间字段拼写、先插入后建表、重复创建视图和反复追加结果等运行问题。删除了全局缓冲区设置，原始数据改为保留；原“路径”改为行为组合，原“跳失率”改为同口径的单次行为用户占比。比例先按聚合总量计算并保留精度，再格式化显示。PV、UV 为无符号整数，环比公式在相减前先转为浮点，以支持下降日的负增长。Tableau 对应字段应使用 `retention_rate.retention_rate` 与 `funnel.funnel_users`；其日期维度保留 `CHAR(10)`，小时维度保留补零的 `CHAR(2)`，以兼容原工作簿的字符串字段。清洗表和日汇总的日期仍采用 MySQL 日期类型。

这些文件经过静态结构和数据口径复核；全量数字由同一源 CSV 的独立重算得到，并核对原 Tableau 保存的行为计数。整理后的 MySQL 脚本未在真实 MySQL 实例执行，因此不应把静态复核表述为通过了全量 MySQL 集成运行。`11_validation.sql` 提供实际运行后的验收方式。
